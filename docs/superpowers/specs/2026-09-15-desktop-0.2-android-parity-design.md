# DUBL Desktop 0.2 Android Functional Parity Design

## Goal

Ship DUBL Desktop 0.2 with functional parity to the canonical Android 0.6.2 application while keeping Android as the source of truth for rules, models, formulas, catalogs, and behavior. Desktop must be desktop-native in layout, avoid horizontal scrolling, persist characters locally, and ship as a click-to-run Linux artifact.

## Non-goals

- No Web/Wasm frontend.
- No server, accounts, or sync.
- No reuse of the historical PySide/Electron desktop architecture or formulas.
- No pixel-for-pixel copy of Android screens.

## Architecture

The existing `shared` KMP module becomes the single source for domain rules and application mutations. Android and Desktop become presentation/platform adapters over the same shared sessions/use-cases. Android-specific persistence and asset readers stay adapters; common catalog models and mutation semantics live in `shared`.

The desktop app uses Compose Desktop as the canonical UI. The portable Linux shell remains only a build/test fallback until the Compose artifact can be produced in CI; it must not contain independent game formulas.

## Shared application surface

Create a shared `CharacterSession` responsible for all mutations currently implemented by Android `CharacterController`: identity, experience, creation state, attributes, resources, skills, development, Chi, magic, equipment, dynamic skills, and character roster operations. Existing `CharacterSheetSession` may delegate to or be folded into this session while keeping its public behavior stable for current tests.

All mutations must call `DublCharacter.normalized()` or the corresponding shared rule object and persist through `CharacterStore`. No desktop-only formulas are allowed.

## Persistence

`AppSnapshot` persistence remains schema-compatible with Android schema 7. Desktop uses a file-backed `CharacterStore` under the user's application data directory. The active character and all `DublCharacter` fields must round-trip. Character sheet extras use a separate platform-independent data model and file-backed desktop store; Android may retain SharedPreferences as an adapter.

## Catalogs

Development, Chi, magic/equipment, and skill-effect catalogs remain canonical JSON data from Android 0.6.2. Desktop receives identical copies as resources/build inputs. Parsing semantics must match Android repositories. Catalog content is never re-authored for desktop.

## Desktop navigation and screens

Desktop navigation retains the current rail/compact responsive shell and exposes:

1. Sheet
2. Skills
3. Development
4. Magic
5. Equipment
6. Characters

### Sheet

Full Android overview parity: identity, portrait path, experience economy, attributes, resources including Chi/custom resources, conditions, derived-stat details, quick skill rolls, learned skills/development summaries, grouping/order data, recent change/undo state where practical, and responsive compact hero behavior.

### Skills

Full catalog, search/filtering, learned-only toggle, rank changes, XP costs, multiple governing attributes, preferred attribute, modifier/formula note, descriptions, hide/restore, custom and specialized skills, deletion of dynamic skills, and roll flow using shared `RollRules`.

### Development

Normal feats, special branches, martial arts, and Chi techniques. Preserve requirements, ability-point/XP economy, option selection, forced purchase state where Android exposes it, parent/child semantics, and current Chi resource behavior.

### Magic

Mana rank/current/max/recovery, school power, schools, spellbook, catalog/custom spells, learn state and XP overrides, usability, search/filtering, and edit/delete flows.

### Equipment

Catalog/custom gear, quantities, carried state, automatic/manual load, capacity/burden, edit/delete, catalog load synchronization, and item details.

### Characters

List, create, select, delete active character, and switch active character without data loss.

## Responsive and UX constraints

- Compact `< 900dp`, normal `900..1319dp`, wide `>= 1320dp`.
- No horizontal scrolling in any screen.
- Long names/descriptions wrap or ellipsize deliberately; they may never expand columns off-screen.
- Only vertical content scrolling is permitted for normal app screens.
- Wide layouts may show master/detail columns; compact layouts stack the same workflow.

## Testing

Every shared mutation is covered by common tests or JVM harnesses. Add a parity matrix test that ensures Android-controller operations have shared equivalents. Add source-boundary tests that reject Android/JVM imports from commonMain. Desktop source tests verify all six workflows are wired and no horizontal scroll is introduced. Packaging smoke tests use a clean HOME and no system Java requirement for the user-facing artifact.

## Release criterion

0.2 is complete only when the parity matrix marks Sheet, Characters, Skills, Rolls, Development, Special Branches, Martial Arts, Chi, Magic, Equipment, XP economy, Conditions, Grouping, Persistence, Catalogs, and Custom Content as PASS and the Linux artifact launches from a clean user environment.
